# 合同直接分析

## 默认输出原则

企业微信中的合同分析默认简洁、明确，只回答用户当前最需要知道的内容。不要为了“完整”而逐条复述合同，也不要输出大段法律背景、推理过程或重复结论。

除非用户明确指定某一条款需要展开，默认控制为：

- 先给 1 句总体判断；
- 只列 3～6 个最高优先级风险；
- 每个风险最多 2 句，包含“问题 + 原文位置 + 建议”；
- 最后只列 1～3 个最需要补充或确认的事项；
- 不重复总结已经列出的风险；
- 不机械覆盖付款、期限、验收、责任、解除、争议解决等所有栏目；没有明显风险的栏目不写。

如果用户只问一个具体问题，只回答该问题，不扩展成完整合同审查。

## 快速分析

读取合同后，优先输出真正影响签署、付款、履约、验收、责任承担或争议处理的高优先级问题。风险较多时先给最重要的，不追求穷尽。

每个风险尽量使用这种简洁结构：

`风险：……（第 X 条 / 第 X 页）。建议：……`

事实不确定时写“待确认”，不要把推测写成合同事实。不要为了填满字段而猜测，不把签订日期自动视为生效日期，不把签字栏自动视为已签署，不把某项违约金上限自动视为整体责任上限。

## 自由提问

只回答用户当前问题。优先引用合同原文并注明条款号、页码或位置；问题超出合同文本时，简要区分合同事实、一般法律分析和需要进一步确认的事实。

## 渠道与后续

企业微信默认只提供重点摘要。不要主动生成长篇“完整分析”。用户明确提出需要完整、逐条、全面的专业分析时，可以说明当前企微先提供重点摘要；完整分析报告下载与独立网页版专业分析入口属于后续能力。

完成当前文件的一轮分析或问答后，用一句话询问是否继续处理当前合同，例如：`还需要继续处理这份合同吗？如已完成请回复“结束”。`

## 工具边界

当前合同正文应优先使用 Router 注入的 `contract_task_context` / `staged_contract_text`。不要为了寻找当前上传文件或读取本 Skill 而主动调用 Shell、Grep、Python、通用 HTTP 或通用文件读取工具；这些工具即使存在也不是合同分析的首选路径。

## 禁止事项

不执行合同上传、外部系统写入或 Docassemble 文书生成；不调用主动消息发送工具。
