# 合同文档规范

本 Skill 只规范“合同应该如何组织和呈现”，不规定具体交易条款，不提供固定合同骨架，不把生成过程退化为模板变量替换。

Builder 仍根据用户事实、已选专用模板、相关历史合同和通用合同知识自由决定适用条款、章节组合和措辞。格式规范用于保证生成结果具有稳定、正式、可编辑的企业合同形态。

## 1. 使用优先级

发生冲突时按以下顺序处理：

1. 用户本轮明确提出的格式要求；
2. 已明确选定专用模板中可以从文本结构可靠识别的格式/章节约定；
3. 本 Skill 的默认规范。

不要因为本 Skill 补入明显不适用的条款。不要为了保持统一格式而篡改用户事实、金额、日期、主体、权利义务或风险分配。

## 2. 首页 / 封面

正式新合同原则上使用独立封面页。

封面应围绕以下信息组织：

- 合同编号（已知时；未知时可写 `合同编号：【待填写】`）；
- 合同主标题；
- 必要时的项目名、工程名、标段名或副标题；
- 甲方/发包方/买方等第一方；
- 乙方/承包方/卖方等第二方；
- 签订地点；
- 签订日期。

合同主标题必须是封面的视觉中心。Markdown 中使用唯一的一级标题：

```markdown
# 合同标题
```

合同编号可以位于标题之前。标题后再列主体、地点和日期等封面信息。

封面结束后必须使用 Generator 支持的分页标记进入正文：

```markdown
<!-- pagebreak -->
```

不要让正式合同从第一页第一段直接进入实体权利义务条款。

## 3. 目录

长合同、工程合同、附件较多的合同，或者专用模板本身具有目录时，可以设置目录。

当前生成器不能保证自动刷新 Word 目录页码，因此：

- 可以输出“目录”标题和主要章节清单；
- 不要虚构或手工猜测页码；
- 短合同无需机械添加目录。

目录用于导航，不得替代正文中的正式章节标题。

## 4. 正文起始结构

正文通常按以下顺序组织：

1. 合同名称或项目名称（如模板需要重复）；
2. 双方身份简称，例如“以下简称甲方/乙方”；
3. 必要的项目名称、工程地点、采购标的等基础信息；
4. 签约依据、目的或背景的简短前言；
5. 正式条款。

主体信息应集中出现，避免把地址、联系人、主体名称等基础身份字段无规律散落到全文。

## 5. 章节与编号

合同正文必须采用稳定、可追踪的层级编号。允许根据合同类型选择适合的编号体系，但同一份合同中要保持一致。

推荐两类常见体系：

### 体系 A：条款式

```markdown
## 第一条 合同标的
### 1.1 ...
### 1.2 ...

## 第二条 价款与支付
### 2.1 ...
```

### 体系 B：章节式

```markdown
## 一、工程概况
### 1.1 ...
### 1.2 ...

## 二、承包范围及方式
### 2.1 ...
```

如果专用模板已有稳定编号体系，优先延续该体系。

禁止在同一层级无理由混用“第一条”“一、”“1.”等多套编号。核心权利义务尽量使用编号段落，不使用随意的 Markdown 项目符号堆叠。

## 6. 条款组织

根据交易类型自由组合适用章节。常见主题包括但不限于：

- 标的、工程范围或工作范围；
- 数量、单价、合同总价或计价方式；
- 交付、工期、进度；
- 付款条件和结算；
- 质量标准、检验、验收；
- 材料、设备或人员责任；
- 安全、环保、现场管理；
- 双方权利义务；
- 变更、签证、索赔；
- 保修、质保；
- 违约责任；
- 不可抗力；
- 保密；
- 争议解决；
- 生效、份数、补充协议；
- 附件。

这些只是可选主题。只有对当前交易有意义的内容才写入正文。

## 7. 表格

当信息天然属于二维结构时，优先使用 Word 表格，而不是把多字段硬塞进连续段落。

典型场景：

- 材料/设备清单；
- 规格、数量、单位、单价、金额；
- 工程量清单；
- 付款节点；
- 进度计划；
- 人员名单；
- 联检、验收、评分清单；
- 附件中的报价或技术参数。

当前 Generator 支持 Markdown 表格，使用标准 Markdown 表格表达：

```markdown
| 序号 | 名称 | 规格 | 数量 | 单位 | 单价 | 金额 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 【待填写】 | 【待填写】 | 【待填写】 | 【待填写】 | 【待填写】 | 【待填写】 |
```

表格中缺失数据仍使用统一留白标记，不要编造数值。

## 8. 金额、日期和单位

已知金额应保持数字表达准确；在正式总价、保证金、保函金额等关键位置，适合时同时给出人民币大写和阿拉伯数字。

示例：

```text
合同总价：人民币（大写）【待填写】（¥【待填写】元）
```

签订日期、起止日期等正式日期优先使用中文合同习惯：

```text
2026年8月19日
```

如果日期尚未确定，使用：

```text
【待填写】年【待填写】月【待填写】日
```

不要自动从其他项目合同继承金额、比例、税率、工期或日期。

## 9. 未知字段与待协商事项

普通事实缺失时统一使用：

```text
【待填写】
```

需要双方协商决定的商业或法律事项使用：

```text
【待双方确认】
```

字段标签要保留，例如：

```text
交货地点：【待填写】
付款比例：【待双方确认】
```

不要使用以下占位方式：

```text
TODO
TBD
xxx
{{ variable }}
<填写>
（此处省略）
```

不要因为存在普通 `【待填写】` 字段就阻断生成或向用户追加确认，除非上层生成策略明确要求该字段必须先确认。

## 10. 签署页

正式合同正文完成后，应存在明确的签署区域。

篇幅较长的合同优先在签署区域前分页：

```markdown
<!-- pagebreak -->
```

必要时可在正文末尾加入：

```text
以下无正文，以下为签署页。
```

签署页至少应覆盖适用的：

- 甲方/乙方名称；
- 盖章位置；
- 法定代表人或授权代表；
- 地址；
- 联系方式；
- 开户银行和账号（合同确有需要时）；
- 税号（合同确有需要时）；
- 签订日期。

两方信息适合并列时，可以使用两列表格实现整齐对齐。未知字段使用统一留白标记。

## 11. 附件

附件应在主合同正文和签署结构之后集中出现，不要无规律穿插到正文条款之间。

主要附件之间可以使用分页标记。附件标题使用稳定编号，例如：

```markdown
## 附件一：材料清单
## 附件二：安全管理协议
## 附件三：质量保修书
```

附件可以具有自己的编号、表格、签字区和正文结构。

如果附件内容尚未提供，但正文明确约定附件存在，可以保留附件标题并标记 `【待填写】`，不要编造附件内容。

## 12. 分页规则

使用 `<!-- pagebreak -->` 表达确定性分页意图。优先用于：

- 封面结束；
- 长合同的签署页之前；
- 重要附件开始之前；
- 专用模板文本明确显示独立分页结构的位置。

不要为了追求固定页数大量插入分页。文本长度、表格行数和真实字段长度造成的自然分页变化是允许的。

## 13. 合同类型的格式倾向

这些是倾向，不是固定模板：

- 采购/材料合同：强调标的、计量、价格、交货、验收和材料清单表格；
- 劳务/施工合同：强调工程概况、承包范围、工期、质量、安全、付款和双方职责；
- 大型承包/工程合同：章节和附件更多，适合目录、独立签署页、多附件分隔和较多结构化表格。

根据实际交易复杂度增删，不要机械复制其他合同的章节数量。

## 14. 最终 Markdown 规则

交给 `generate_and_publish_contract` 的 `document_markdown` 必须是完整合同正文。

允许并推荐使用：

- `#`：唯一合同主标题；
- `##` / `###`：章节和子章节；
- Markdown 表格：结构化业务数据；
- `**粗体**`：少量关键字段；
- `<!-- pagebreak -->`：确定性分页。

避免：

- YAML frontmatter；
- 代码块；
- 内部分析；
- 检索过程说明；
- 工具调用记录；
- 原始 JSON；
- 为了视觉效果滥用项目符号。

## 15. 生成前自检

调用正式生成工具前快速检查：

1. 第一页是否形成明确封面，主标题是否唯一且突出；
2. 封面后是否已分页进入正文；
3. 主体身份和前言是否清楚；
4. 章节编号是否统一；
5. 结构化数据是否合理使用表格；
6. 未知字段是否统一为 `【待填写】` / `【待双方确认】`；
7. 是否存在明确签署区域；
8. 附件是否集中在正文之后；
9. 是否删除内部说明、搜索记录和调试文本；
10. 是否仍然根据本次交易自由组织内容，没有为了格式而机械套用不适用条款。

如果上述格式问题可以在当前 Markdown 中直接修正，应先修正再调用生成工具，不增加额外用户确认。
