# 正式合同文档规范

## 内容与格式边界

当前交易事实、用户要求以及经用户同意采用的模板/历史资料决定合同内容。本 Skill 负责把结果整理成稳定、正式、可编辑的合同文件。

冲突时按以下优先级处理：

1. 用户本轮明确格式要求；
2. 已明确采用的专用模板结构；
3. 本 Skill 默认规范。

格式规则不得篡改主体、金额、日期、权利义务或风险分配，也不得为了完整感强行加入明显不适用条款。

## 默认结构

正式新合同通常包含：

- 清晰的合同主标题；
- 双方主体和必要基础信息；
- 简短前言/签约背景（适用时）；
- 有稳定编号的正式条款；
- 适用的结构化表格；
- 明确的签署区域；
- 附件（如有）。

长合同可使用独立封面、目录和签署页；短合同无需机械增加页面。

## 标题与编号

同一份合同保持一种稳定编号体系，例如：

```text
第一条 ...
1.1 ...
1.2 ...
```

或：

```text
一、...
1.1 ...
1.2 ...
```

不要无理由混用多套同级编号。

## 表格

天然属于二维信息的内容优先使用表格，例如：

- 材料/设备清单；
- 数量、单价、金额；
- 付款节点；
- 进度计划；
- 验收清单；
- 技术参数；
- 双方签署信息。

## 未知字段

普通事实缺失：

`【待填写】`

需要双方协商决定：

`【待双方确认】`

不要为了填满字段而从历史合同猜值。不要使用 `TODO`、`TBD`、`xxx` 或模板变量语法作为正式留白。

## 历史数据

历史合同可以影响结构、条款组合和措辞。主体、项目名、合同编号、金额、单价、数量、日期、付款比例、质保比例、违约比例、税率、银行账户、地址、工期等项目特定数据默认不得继承。

## 签署与附件

正文末尾应有清晰签署区。根据实际需要包含名称、盖章、法定代表人/授权代表、地址、联系方式、银行账户、税号、签订日期等字段；不需要的字段不要机械添加。

附件集中在正文之后，使用稳定标题和编号。附件内容缺失时可以保留标题并标注 `【待填写】`，不要编造。

## 修改现有合同

- 以用户明确指定版本为修改源；
- 默认产生新文件，不覆盖源文件；
- 保持未要求修改的内容稳定；
- 若同时采用数据库资料，最终说明哪些来源影响了哪些修改。

## 最终自检

生成正式文件前检查：

1. 主体、项目事实是否来自可靠来源；
2. 编号和层级是否一致；
3. 表格是否用于真正适合的结构化信息；
4. 未知字段是否正确留白；
5. 是否存在签署区；
6. 附件顺序是否清楚；
7. 是否混入检索日志、工具 JSON、内部分析或认证信息；
8. 是否错误继承了历史项目具体值；
9. 是否按用户要求保留/改变指定内容。

Harness 能直接创建 DOCX 时优先使用其原生文件能力；否则使用项目后续提供的确定性 renderer。
